# 查新与打分细则

对应 SKILL 第 5、6 步。来源是视频1「先让它做文献综述」、视频2 的 Prompt 2、查新卡片、漏检反例和打分表，加上本 skill 实际跑 agent 方向点子时用过的做法。

> 视频2 的教训：三个 AI 里有两个漏掉了已有工作，其中一个一边说「没有论文」一边打了最高分（视频2 [03:19–03:41]）。所以 AI 的查新只是线索，结论要靠人打开全文核对。

---

## 1. 检索渠道

| 渠道 | 用途 | 注意 |
| --- | --- | --- |
| arXiv API（export.arxiv.org） | 主力，按关键词和日期窗口批量取摘要 | 编号、标题、日期以 API 返回为准；可以把结果缓存成 JSON 方便复查 |
| arXiv 网页 / 全文 PDF | 读最接近的 3–5 篇全文 | 重点看实验、消融、附录；用 poppler（pdftotext）转文本 |
| Semantic Scholar | 查引用链：最接近的论文被谁引用了 | 新论文常常就在引用链里 |
| Google Scholar / 网页搜索 | 补 arXiv 以外的会议论文、博客、代码仓库 | 博客和推文不算论文，只当线索 |
| OpenReview | 查 ICLR / NeurIPS 等投稿和审稿意见 | 被拒稿件也算「有人做过」 |
| ACL Anthology | NLP 相关方向 | |

至少用两个渠道。只用了一个时，结论旁写明。

## 2. 检索词

- 每个点子至少 5 组检索词：核心术语、同义词、英文缩写、方法名、现象名。
- 同时搜「现象」和「方法」：例如既搜 "agent repeats failed actions"，也搜 "contrastive decoding agent"。
- 记下用过的检索词，交付时可以说明覆盖范围。

## 3. 时间窗口

- **主窗口：** 最近 6 个月。用来写「近半年脉络」和判断撞车风险。
- **查新不限日期：** 判断「有没有人做过」时要回查更早的工作，经典方法往往是最接近的那篇。
- 交付时把近半年的工作和更早的工作分开列。

## 4. yes / partly / no 判定

| 结论 | 判定标准 | 下一步 |
| --- | --- | --- |
| **yes** | 有论文在相同设置下做了相同的关键操作，并报告了结果 | 当基线。找它留下的缺口：没做的设置、没解释的现象、没做的消融。找不到缺口就换题 |
| **partly** | 关键操作相同但设置不同（如单轮 vs 多轮、RAG vs agent、离线 vs 在线、训练 vs 免训练），或设置相同但关键操作不同 | 写清「相同 / 不同」，不同点必须是审稿人会认可的实质差异 |
| **no** | 读过最接近的 3–5 篇全文后，都没有做这个关键操作 | 仍要写最接近的那篇和区别；交付时说明「没找到」不等于「没人做过」 |

热门方向（如 agent）里，大多数点子会落在 yes 或 partly。这是常态，不是失败。本 skill 跑 agent 方向时，28 个候选里 13 个基本已做、15 个部分做过，没有一个能有把握说完全没人做过。

## 5. 全文核对清单

进入第 7 步的点子，最接近的 3–5 篇必须读全文，每篇回答：

- [ ] 它是否做了本点子的关键操作？在哪一节？
- [ ] 设置有什么不同（任务、单轮/多轮、训练/免训练、模型规模）？
- [ ] 附录或消融里有没有已经覆盖本点子？
- [ ] 它的数据有没有直接否定本点子的预测？
- [ ] 审稿人会不会说本点子是它的「简单扩展」？反驳理由是什么？
- [ ] 作者单位：是否大公司（按署名）？

只读了摘要的，在结论旁标「只看了摘要」，并在风险里写明哪几篇可能在正文里已经覆盖。

## 6. 查新表

| 点子 | 结论 | 最接近的论文（编号 + 标题 + 日期） | 单位 | 相同 | 不同 / 缺口 | 依据 |
| --- | --- | --- | --- | --- | --- | --- |
| | yes / partly / no | | 大公司单独标 | | | 全文 / 摘要 |

## 7. 大公司工作怎么标

- 只按论文署名或作者主页判断。
- 用了某公司的模型（如在 Qwen、Llama 上做实验）不等于该公司的论文。
- 交付时单独一行或一节列出，例如「大公司相关：XXXX（Google DeepMind 署名）」。
- 核实不了单位的，写「单位未核实」，不要猜。

## 8. 打分锚点（本 skill 的约定，不是官方审稿表）

视频2 用 soundness、originality、significance 三项，满分 45（三位 AI 审稿人各 15），没有展示每项怎么拆。本 skill 统一改成**每项 1–10 分**，并给下面的锚点，方便比较。

### Soundness（严谨性：合理吗、逻辑吗）

| 分 | 锚点 |
| --- | --- |
| 9–10 | 受控对比，只改一个因素；判分是确定的；竞争假说给出相反预测；有证伪条件 |
| 7–8 | 设计合理，但有一个审稿人会追问的外推问题（如玩具任务、单一环境） |
| 5–6 | 能跑，但混杂因素没排除；或判分依赖 LLM judge |
| 3–4 | 实验结果无论如何都能被解释成支持结论 |
| 1–2 | 无法检验 |

### Originality（原创性）

| 分 | 锚点 |
| --- | --- |
| 9–10 | 查新为 no，且关键操作在相邻领域也没有先例 |
| 7–8 | 现象已知，但拆解方法或机制解释没找到先例 |
| 5–6 | 已有方法搬到新设置，加一处实质改动（例如「SSFO 搬到多轮 agent + 环境核实」） |
| 3–4 | 已有方法搬到新设置，没有实质改动 |
| 1–2 | 查新为 yes，且没有缺口 |

### Significance（重要性）

| 分 | 锚点 |
| --- | --- |
| 9–10 | 会改变很多人的默认做法 |
| 7–8 | 直接影响一类系统的设计（如长程 agent 是否需要清洗历史），或解释一个广泛观察到的现象 |
| 5–6 | 对一个子方向有用 |
| 3–4 | 只对特定设置有用 |
| 1–2 | 做成了也没人会用 |

### 打分规则

1. 查新为 yes 时，原创性不超过 4；partly 时不超过 7，除非写清楚实质差异。
2. 至少 2 个独立的 AI 审稿人；分歧超过 2 分的项，追问双方理由。
3. 每个分数都追问一次「为什么」，并要求给出「提高 2 分需要补什么」。
4. 交付时写分数，并写出原创性或其他低分项的扣分原因（例如「原创性只有 6，是因为机制上接近 XXX」）。
5. 分数只是辅助，最终取舍由人做。视频2 的表里五条几乎打平，说明 AI 打分区分度有限。

## 9. 写作阶段的五项清单（视频4）

连贯、全面、解释清楚、站得住脚且讲得通、最好是新的。视频4 作者说这是「ICML 会议论文的接收标准」，但没有引用官方文件，未核实。和上面三项是两份不同的清单（张力 9），写作阶段用这份，选题阶段用三项。
